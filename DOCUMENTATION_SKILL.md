# DOCUMENTATION SKILL — правила оформления документации moduleBox

Стандарт оформления страниц вики moduleBox. Документ описывает **единый стиль**
для всех страниц: программных модулей, аппаратных модулей, платформенных разделов.

> [!important]
> Протокол обмена (структура топика, направления `event`/`action`, формат payload,
> словарь имён) задан **конституцией**: `moduleBox/CONSTITUTION.md` в репозитории
> прошивки и её вики-версия [[Платформа moduleBox/Конституция|Конституция]].
> Любая страница модуля обязана ей соответствовать. Если код и конституция
> расходятся — это баг кода, а не повод писать по-старому.

---

## 1. ОБЩИЕ ПРИНЦИПЫ

### 1.1 Формат
- Markdown (.md), движок **Quartz 4**, синтаксис **Obsidian**: wikilinks `[[]]`,
  embeds `![[]]`, callouts `> [!note]`.
- Язык — русский. Имена опций, топиков, команд, событий — на английском, как в коде.

### 1.2 Расположение
```
content/
  ├── Программные модули/
  │   ├── {mode}_sw.md
  │   ├── Виртуальные модули/{mode}_sw.md
  │   ├── Звуковые модули/{mode}_sw.md
  │   ├── Дальномеры/{mode}_sw.md      ← семейство distanceSens
  │   ├── Кнопки с подсветкой/{mode}_sw.md ← семейство button_*
  │   ├── Входы и выходы/{mode}_sw.md   ← компонент in_out (in_*, out_*, relay, tachometer)
  │   └── _assets/
  ├── Аппаратные модули/
  │   ├── {name}_hw.md
  │   └── _assets/
  ├── Устройства/
  └── Платформа moduleBox/
```

### 1.3 Именование файлов
- Программный модуль: `{mode}_sw.md`, где `{mode}` — значение `mode =` в `config.ini`.
- Аппаратный модуль: `{name}_hw.md`.
- Имя файла = имя режима в конфигурации. Расхождение недопустимо.

### 1.4 Источник правды
Порядок приоритета при любом расхождении:

1. **`manifest.json`** (генерируется из doc-комментариев прошивки; в сборке лежит
   как `build/esp-idf/*/generated_files/gen_*.h`) — имена опций, диапазоны,
   значения по умолчанию, полные имена событий и команд.
2. **Исходники прошивки** — если модуль ещё не попал в манифест.
3. Конституция — для формы топика и payload.

Старая документация источником правды **не является**: то, что модуль
документирован, ничего не говорит о том, что он документирован верно.

Разделы идут строго в этом порядке. Отсутствующие — пропускаются, порядок
оставшихся не меняется.

```markdown
---                     ← frontmatter
```ini                  ← блок mode
## Совместимость        ← ссылки на HW-модули
## Принцип работы
## Топики
## Опции
## События              ← только если модуль что-то рапортует
## Команды              ← только если модуль что-то принимает
## Режимы анимации      ← только LED-модули с опцией ledMode
## Индикация            ← необязательный
## Примеры
## Пример подключения   ← необязательный, SVG-схема
```

## 3. FRONTMATTER

```yaml
---
title: имя модуля
draft: false
tags:
  - sw
  - button
---
```

- **title** — имя режима (`button_led`) либо короткое русское название. Единообразно
  внутри раздела: программные модули озаглавлены именем режима, аппаратные — русским
  названием.
- **draft** — `false` для опубликованных. `true` — для страниц по не мигрированным
  или экспериментальным модулям.
- **tags** — необязательные.

Типичные теги:

| Тег | Назначение |
|-----|-----------|
| `sw` / `hw` | программный / аппаратный модуль |
| `virtual` | виртуальный модуль (без железа) |
| `input` / `output` | вход / выход |
| `button` | кнопка |
| `led` / `smartLed` | светодиоды / адресные светодиоды |
| `sound` / `player` | звук / проигрыватель |
| `distance` | датчик расстояния |
| `uart` / `i2c` | используемый интерфейс |

## 4. БЛОК MODE

Сразу после frontmatter, перед описанием, с подсветкой `ini`:

````markdown
```ini
[SLOT_n]
mode = button_led
```
````

Если модуль работает не в любом слоте — указать диапазон из манифеста (`slots`):

````markdown
```ini
[SLOT_0] ;только нулевой слот
mode = mp3Player
```
````

За блоком — одно-два предложения о назначении модуля.

## 5. РАЗДЕЛ «СОВМЕСТИМОСТЬ»

Список аппаратных модулей, с которыми работает программный:

```markdown
## Совместимость
- [[Аппаратные модули/button_led_hw|Модуль кнопка с подсветкой]]
- [[Аппаратные модули/in_out_hw|Модуль вход-выход]]
```

Для виртуальных модулей раздел заменяется строкой:

```markdown
## Совместимость
Виртуальный модуль, аппаратной части не требует. Занимает слот из диапазона 0–9.
```

Связь двусторонняя: HW-страница перечисляет совместимые SW-модули, SW-страница — HW.

## 6. РАЗДЕЛ «ТОПИКИ»

Топик собирается по конституции:

```
<deviceName>/<модуль>_<слот>/<направление>/<имя>
```

Раздел описывает **базу** топика — то, что стоит до направления. Полные имена
событий и команд перечисляются в своих разделах, дублировать их здесь не нужно.

```markdown
## Топики
База топика события:
- `<deviceName>/button_<slot>` — например `moduleBox/button_0`

База топика действия:
- `<deviceName>/led_<slot>` — например `moduleBox/led_0`

Полный топик — база плюс направление и имя: `moduleBox/button_0/event/press`,
`moduleBox/led_0/action/setMaxBright`.
```

Правила:
- База берётся из манифеста (`trigger` / `action`), не выдумывается.
- У модуля может быть одна база (`stepper`) или две разные (`button_led`: события
  под `button_<n>`, команды под `led_<n>`).
- Если модуль только рапортует (`tenzoButton`) — раздела действия нет, и наоборот.
- Если модуль позволяет задать нестандартный топик опцией (`buttonTopic`,
  `ledTopic`, `topic`) — упомянуть это здесь одной строкой.

## 7. РАЗДЕЛ «ОПЦИИ»

Формат строки:

```markdown
- **имяОпции** — *тип*, описание. Диапазон. По умолчанию {значение}.
```

Типы и их соответствие коду:

| Тип в документации | Функция в коде | valueType в манифесте |
|---|---|---|
| *флаг* | `get_option_flag_val()` | `flag` |
| *число(int)* | `get_option_int_val()` | `int` |
| *число(float)* | `get_option_float_val()` | `float` |
| *строка* | `get_option_string_val()` | `string` |
| *строка(enum)* | `get_option_enum_val()` | `enum` |

Обязательные атрибуты:
- числовые — диапазон, значение по умолчанию, единицы измерения ($мСек$, $см$, $Гц$);
- флаги — только описание эффекта;
- enum — перечисление допустимых значений вложенным списком, с пометкой «по умолчанию».

```markdown
- **ledMode** — *строка(enum)*, режим анимации:
	- *none* — без анимации (по умолчанию)
	- *flash* — вспышки с равными промежутками
```

Если модуль имеет несколько функциональных частей — опции группируются подзаголовками
жирным текстом, а не отдельными `###`:

```markdown
## Опции
Доступные опции для кнопки:
- **buttonInverse** — ...

Доступные опции для подсветки:
- **ledInverse** — ...
```

⚠️ **Критично:**
- Имя, диапазон и значение по умолчанию — точно как в манифесте/коде.
- Опции, которых нет в `get_option_*_val()`, документировать нельзя (опции-призраки).
- Вычисляемые величины (`increment` из `fadeTime`) — не опции.

## 8. РАЗДЕЛ «СОБЫТИЯ»

Модуль **сообщает** миру — направление `event`. Оформляется таблицей: конституция
разносит имя (в топик) и значение (в payload), таблица это показывает наглядно.

```markdown
## События
| Топик | Payload | Описание |
|---|---|---|
| `button_<slot>/event/press` | `0` / `1` | Изменение состояния кнопки |
| `button_<slot>/event/longPress` | `0` / `1` | Длинное нажатие, при `longPressTime` > 0 |
```

Правила:
- В колонке «Топик» — часть после `<deviceName>/`, в моноширинном начертании.
- В колонке «Payload» — допустимые значения либо тип (`целое`, `0.0–1.0`, `R G B`).
- Каждый `stdreport_register()` в коде = одна строка таблицы. Лишних строк нет.
- Событие `event/enable` документируется, если модуль его регистрирует.
- После таблицы — пример полного сообщения:

```markdown
Пример: топик `moduleBox/button_0/event/longPress`, payload `1`.
```

❌ Нельзя писать `moduleBox/button_0/longPress:1` как топик. Запись `имя:значение` —
человеческая нотация из конфигурационного файла и crossLink, в MQTT её нет.

## 9. РАЗДЕЛ «КОМАНДЫ»

Модуль **принимает** — направление `action`. Тот же табличный формат:

```markdown
## Команды
| Топик | Payload | Описание |
|---|---|---|
| `led_<slot>/action/setMaxBright` | `0`–`255` | Максимальная яркость |
| `led_<slot>/action/toggleLedState` | — | Переключить состояние |
| `led_<slot>/action/enable` | `0` / `1` | Усыпить / разбудить модуль |
```

Правила:
- Каждый `stdcommand_register()` = одна строка. Имя команды берётся из манифеста
  целиком, вместе с многосегментными именами (`action/ch_0/setBright`).
- Команда без параметров (`PARAMT_none`) — в payload прочерк `—`.
- `action/enable` описывается всегда, когда зарегистрирован, и всегда последней строкой.
- Безымянных команд в конституции нет: у каждого действия есть `name`.

## 10. РАЗДЕЛ «РЕЖИМЫ АНИМАЦИИ»

Только для модулей с опцией `ledMode`. Список режимов **точно совпадает** с
перечислением в `get_option_enum_val()`:

```markdown
## Режимы анимации
- **none** — без анимации (по умолчанию).
- **flash** — вспышки с равными промежутками времени.
```

## 11. РАЗДЕЛ «ПРИМЕРЫ»

````markdown
## Примеры

```ini
[SLOT_2]
mode = button_led
options = ledMode:flash, maxBright:255, fadeTime:500
;включить подсветку при нажатии кнопки
crosslink = button_2/event/press:1->led_2/action/enable:1
```
Пояснение к примеру: что произойдёт и почему.

Подробнее — [[Платформа moduleBox/CrossLink|внутренние связи (crossLink)]].
````

Правила:
- Подсветка `ini`, комментарии через `;` над строкой, к которой относятся.
- Все опции из примера обязаны существовать в разделе «Опции».
- Топики в `crosslink` — полные, с направлением: `button_2/event/press` →
  `led_3/action/enable`. Имя устройства в crossLink не пишется.
- Событие-источник crossLink должно принадлежать **тому слоту**, в блоке которого
  объявлена связь.
- В конце раздела — ссылка на страницу crossLink.

- «Схема подключения» — embed сгенерированной SVG-схемы.

## 13. СХЕМЫ ПОДКЛЮЧЕНИЯ

Схемы **генерируются**, не рисуются руками:

- описание — `content/.../_assets/<модуль>.scheme.yaml`;
- генерация — `python tools/scheme_gen/generate.py "<файл>.scheme.yaml"`;
- формат YAML — `tools/scheme_gen/README.md`;
- рабочий процесс — скилл `connection-scheme`.

Встраивание: `![[Аппаратные модули/_assets/<модуль>.svg]]`.

## 14. ПЕРЕКРЁСТНЫЕ ССЫЛКИ

```markdown
[[Программные модули/button_led_sw|button_led]]
[[Платформа moduleBox/CrossLink|crossLink]]
![[Программные модули/_assets/ledRing.gif]]
[[#Режимы анимации]]
```

- Ссылки — полным путём от `content/`.
- HW ↔ SW ссылаются друг на друга.

> [!warning]
> **Ссылки внутри таблиц.** Wikilink с алиасом в ячейке таблицы ломает разбиение
> строки: экранированный `\|` съедает следующий разделитель, и соседние ячейки
> слипаются. В таблицах используйте обычную markdown-ссылку, а путь с пробелами
> берите в угловые скобки:
>
> ```markdown
> | [soundMono](<Аппаратные модули/soundMono_hw.md>) | 201-005 | Описание |
> ```
>
> Путь отсчитывается от корня `content/` — в конфигурации Quartz задано
> `markdownLinkResolution: "absolute"`.
- Новая страница модуля добавляется в `content/index.md` в соответствующий раздел,
  аппаратная — ещё и в таблицу [[Аппаратные модули/Выбор модуля|Выбор модуля]].

## 15. ФОРМАТИРОВАНИЕ

| Элемент | Формат | Пример |
|---------|--------|--------|
| Имя опции | `**жирный**` | **buttonInverse** |
| Тип опции | `*курсив*` | *флаг*, *число(int)* |
| Топик, payload, режим | `` `моноширинный` `` | `moduleBox/button_0/event/press` |
| Важная заметка | `==выделение==` | ==Нумерация слотов с нуля.== |
| Устаревшее | `~~зачёркнуто~~` | ~~старый формат~~ |
| Единицы измерения | `$LaTeX$` | $мСек$, $см$, $шаг/сек^2$ |

Callout-блоки:

```markdown
> [!note]
> Обычное замечание.

> [!warning]
> Расхождение прошивки с конституцией, известное ограничение.

> [!example]-
> Свёрнутый пример.
```

Топики и значения оформляются моноширинным начертанием, **не** курсивом в кавычках.
Старый стиль `*"deviceName/button_0"*` заменяется на `` `moduleBox/button_0` ``.

## 16. КОНТРОЛЬНЫЙ СПИСОК

### Структура
- [ ] Frontmatter с `title` и `draft`
- [ ] Блок `mode` присутствует, имя совпадает с диспетчером `me_slot_config.c`
- [ ] Разделы в порядке из §2

### Соответствие конституции
- [ ] Все топики четырёхуровневые: `<dev>/<модуль>_<слот>/<direction>/<name>`
- [ ] Имя события/команды — в топике, значение — в payload; нет записи `топик:значение`
- [ ] Направления не перепутаны: рапорт — `event`, команда — `action`
- [ ] `enable` описан там, где зарегистрирован
- [ ] Имена взяты из канонического словаря, если для явления есть каноническое имя

### Опции
- [ ] Каждая опция из манифеста описана, лишних нет
- [ ] Имена, диапазоны, значения по умолчанию совпадают с манифестом
- [ ] Типы соответствуют функциям `get_option_*_val()`
- [ ] Нет опций-призраков и вычисляемых величин

### События и команды
- [ ] Каждый `stdreport_register()` — строка в «События»
- [ ] Каждый `stdcommand_register()` — строка в «Команды»
- [ ] Многосегментные имена (`ch_0/setBright`) записаны целиком
- [ ] Команды без параметров помечены прочерком

### Примеры и ссылки
- [ ] Опции примера существуют в разделе «Опции»
- [ ] crossLink записан с направлениями и без имени устройства
- [ ] HW ↔ SW ссылки на месте, битых ссылок нет
- [ ] Страница добавлена в `index.md`

## 17. ТИПИЧНЫЕ ОШИБКИ

### 17.1 Доконституционный формат
| Было | Стало |
|---|---|
| `moduleBox/button_1:1` | топик `moduleBox/button_1/event/press`, payload `1` |
| `moduleBox/led_3/toggleLedState` | `moduleBox/led_3/action/toggleLedState` |
| `moduleBox/player_0/play:2` | топик `moduleBox/player_0/action/play`, payload `2` |
| `crosslink = button_2:1->led_3:1` | `crosslink = button_2/event/press:1->led_3/action/enable:1` |

### 17.2 Устаревшие имена
| Старое | Актуальное |
|---|---|
| `radar_` | `distanceSens_` |
| `pwmRGB` / `pwmRGB_` | `pwmLeds` / `pwmLeds_` |
| `fadeIncrement` | `fadeTime` |
| `increment` как опция | вычисляется из `fadeTime` |
| `out_0:1` | `out_0/action/setVal`, payload `1` |

### 17.3 Опции-призраки
Поля структуры, не читаемые из конфигурации, документировать нельзя:
`inReportDelay`, `outDelay`, `outImpulse` (это команда, а не опция).

### 17.4 Путаница направлений
- `event` — модуль **отправляет**;
- `action` — модуль **принимает**;
- `ledTopic`, `outTopic` задают базу топика **действия**, а не события.

## 18. ШАБЛОН ПРОГРАММНОГО МОДУЛЯ

````markdown
---
title: имя_модуля
draft: false
tags:
  - sw
---
```ini
[SLOT_n]
mode = имя_модуля
```
Краткое описание модуля в одно-два предложения.

## Совместимость
- [[Аппаратные модули/module_hw|Название аппаратного модуля]]

## Принцип работы
Что модуль делает, когда рапортует, чем управляет.

## Топики
База топика события:
- `<deviceName>/prefix_<slot>` — например `moduleBox/prefix_0`

База топика действия:
- `<deviceName>/prefix_<slot>` — например `moduleBox/prefix_0`

Полный топик — база плюс направление и имя.

## Опции
Доступные опции:
- **optionName** — *тип*, описание. По умолчанию {значение}.

## События
| Топик | Payload | Описание |
|---|---|---|
| `prefix_<slot>/event/val` | целое | Текущее значение |

## Команды
| Топик | Payload | Описание |
|---|---|---|
| `prefix_<slot>/action/setVal` | целое | Задать значение |
| `prefix_<slot>/action/enable` | `0` / `1` | Усыпить / разбудить модуль |

## Примеры

```ini
[SLOT_n]
mode = имя_модуля
options = option1:value1
crosslink = prefix_n/event/val:@->target_m/action/setVal:@
```
Пояснение к примеру.

Подробнее — [[Платформа moduleBox/CrossLink|внутренние связи (crossLink)]].
