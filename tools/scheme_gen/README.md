# Генератор схем подключения

`generate.py` строит SVG-схему подключения moduleBox из YAML-описания.
Раскладка одинакова для всех схем — задаётся только содержимое.

## Запуск

```sh
python tools/scheme_gen/generate.py "<путь>/<имя>.scheme.yaml"
# -> рядом появится <имя>.svg

python tools/scheme_gen/generate.py "<...>.scheme.yaml" -o tmp/preview.svg   # в указанный файл
python tools/scheme_gen/generate.py "<...>.scheme.yaml" --pdf                # + PDF (Inkscape)
```

## Схема контроллера из config.ini (schemes_workspace)

Для проектной документации схема собирается **из конфига контроллера**:

```
schemes_workspace/<Проект>/<контроллер>/
    config.ini            <- кладётся руками
    <deviceName>.scheme.yaml   <- from_config.py; сюда вносятся ручные правки
    <deviceName>.svg / .pdf    <- generate.py
```

```sh
python tools/scheme_gen/build.py schemes_workspace/<Проект>/<контроллер>   # весь конвейер
python tools/scheme_gen/build.py schemes_workspace/<Проект>                # все контроллеры
python tools/scheme_gen/build.py <папка> --force      # пересоздать YAML из config.ini
python tools/scheme_gen/from_config.py <config.ini>   # только шаг config -> YAML
```

`from_config.py` **не перезаписывает** существующий YAML без `--force` — в нём
живут ручные правки (цвета проводов, артикулы БП, подписи). `build.py`
пропускает шаг config→YAML, если YAML уже есть.

Что читается из конфига:

| Откуда | Что | Куда на схеме |
|---|---|---|
| `[SYSTEM] deviceName`, `boardVersion` | имя, версия платы | шапка контроллера |
| `[SYSTEM]` комментарий `;12v 100w mountPlate` | БП под контроллером (12V 100W) + пометка «монтажная плита» | блок `psu`, `notes` шапки |
| `[LAN] LAN_enable / DHCP / ipAdress / netMask` | `10.10.3.211/24` или `DHCP`; при `LAN_enable=0` Ethernet не рисуется | строка разъёма Ethernet |
| `[SLOT_n] mode` | аппаратный модуль (таблица `modes` в базе) | модуль в слоте `s_n` |
| `[SLOT_n]` комментарий | тип нагрузки, подпись, флаги | устройства слева + жгуты |
| `crosslink` между слотами | `setHomingSensor` / `setUpLimit` / `setDownLimit` | примечание на датчике («датчик нуля stepper_0») |

**Комментарий слота:** `;<тип>[_xN] [подпись...] [флаги...] [<тип2> ...]`

- тип — из базы нагрузок (`stepper`, `opticSensor`, `solenoid`, `button`…),
  регистр не важен; `_x2` — две одинаковые нагрузки на `ch_0`, `ch_1`;
- типа нет — берутся нагрузки по умолчанию для `mode`;
- несколько типов подряд (`opticSensor solenoid`) — каждый занимает
  свободный канал своего рода (in / out); порядок не важен;
- флаги: `OCjumper` — перемычка OC на **канале** модуля (плашка «OC» у пина
  канала, занятого этой нагрузкой; `opticSensor_x2 OCjumper` — на обоих,
  `opticSensor OCjumper opticSensor` — только на ch_0), `NPN`/`PNP`/`NO`/`NC`
  (бейдж на нагрузке; `NC` у реле переключает контакт), `DCDC` — понижающий
  преобразователь-«насадка» на слоте (`;servo 5V DCDC` → квадрат «DC-DC
  12V → 5V» слева от модуля, жгут к нагрузке идёт от его пинов);
- `none` — модуль стоит, но ничего не подключено (рисуется только модуль);
- текст в кавычках (`'энкодер свитка'`) — назначение блока: печатается серой
  строкой под названием, а не внутри него;
- остальные слова — подпись нагрузки (модель; «48V» у `stepper`/`servoStepper`
  уходит в имя БП и из подписи мотора убирается).

Двухпроводные нагрузки (соленоид, двигатель, лента) подключаются по типу
выхода модуля (`out_kind` в базе): `out_2ch` — push-pull, нагрузка между
`ch` (+) и `gnd` (−); `3n_mosfet` — open drain, между `V+` (+) и `ch` (−).

База нагрузок и пины модулей: `.claude/skills/connection-scheme/loads.yaml`
(формат описан в шапке файла). Виртуальные режимы (`listOfActions`,
`startup`…) пропускаются; пустые слоты не рисуются.

Требуется PyYAML: `python -m pip install pyyaml`.

Файл описания кладётся рядом с картинкой: `_assets/<модуль>.scheme.yaml`,
генерируется в `_assets/<модуль>.svg`, который встраивается в страницу через
`![[Программные модули/_assets/<модуль>.svg]]`.

## Раскладка (фиксированная)

- **Контроллер** — справа: шапка (имя + пустой блок под серийный номер),
  разъёмы Ethernet/USB, модули (1–6), **модуль питания всегда внизу**.
- **ПК-сервер** — опционально над контроллером.
- **Блок питания** — опционально под контроллером.
- **Устройства** (драйверы, нагрузки, датчики) — слева, пины подписаны.
- **Жгуты** — пронумерованы, рисуются толстой линией; цветные «хвосты»
  проводов расходятся к пинам у обоих концов.

Пины модулей нумеруются с нуля. Цвет провода задаётся **один раз** —
поэтому на обоих концах жгута он совпадает по построению.

## Формат YAML

```yaml
title: "stepper — пример подключения"   # подпись сверху (необязательно)

controller:
  name: ModuleBox
  serial: ""                # текст в блоке серийного номера ("" -> "S/N")
  server: false             # true или строка -> блок «ПК / сервер» сверху
  board: "плата v4"         # подпись под именем (необязательно)
  notes: ["монтажная плита"]  # мелкие пометки в правой части шапки
  connectors: [Ethernet, USB]   # или {name: Ethernet, label: "10.10.3.211/24"}
  modules:                  # 1–6 модулей, сверху вниз
    - name: out_2ch
      id: s0                # ключ для адресации пинов (иначе используется name)
      slot: s_0             # подпись слота (необязательно)
      mode: stepper         # подпись «mode: …» под именем (необязательно)
      badges: ["OC jumper"] # «пилюли» в теле модуля (необязательно)
      pin_badges: {ch_0: [OC]}   # «пилюли» у конкретных пинов (необязательно)
      pins: [Vbus, ch_1, ch_0, gnd]
      attachment:           # «насадка» слева от модуля, часть контроллера (необязательно)
        name: "DC-DC\n12V → 5V"
        pins: ["+5V", gnd, ch_0]   # адресуются как attach:<id модуля>:<pin>
  power_module:             # модуль питания, всегда внизу стека
    name: Power
    pins: ["+", "-"]
  psu:                      # блок питания под контроллером (необязательно)
    name: "Блок питания\nMW RS-25-12"
    pins: ["+12", gnd]

devices:                    # устройства слева, сверху вниз
  - id: driver              # короткий id для адресации пинов
    name: "Драйвер\nдвигателя"   # \n -> перенос строки
    notes: ["датчик нуля stepper_0"]  # серые строки под именем (можно note: "строка")
    badges: [NPN]           # «пилюли» в правой части шапки (необязательно)
    pins: ["+48", gnd, "dir+", A, B]

harnesses:                  # жгуты
  - id: 1
    label: "step / dir"     # подпись в легенде (необязательно)
    wires:
      - {a: "module:out_2ch:ch_0", b: "device:driver:dir+", color: yellow}
```

### Адреса пинов (endpoint)

| Префикс             | Что          |
|---------------------|--------------|
| `device:<id>:<pin>` | пин устройства слева |
| `module:<id>:<pin>` | пин модуля контроллера (`id`, а если его нет — `name`) |
| `attach:<id>:<pin>` | пин «насадки» на модуле (DC-DC и т.п.) |
| `power:<pin>`       | пин модуля питания контроллера |
| `psu:<pin>`         | пин блока питания под контроллером |

Имена пинов со спецсимволами (`+`, `-`, цифра в начале) берутся в кавычки;
`NO`/`NC` тоже (иначе YAML прочитает `NO` как `false`). Повторяющиеся пины
адресуются с суффиксом: `COM`, `COM.2`.

### Цвета проводов

`red`, `black`, `blue`, `green`, `yellow`, `orange`, `white`/`gray`,
`brown`, `violet`. Можно указать и hex (`color: "#aa33cc"`).

## Замечания

- Жгут «устройство ↔ устройство» прижимается к устройствам,
  «контроллер ↔ блок питания» — к контроллеру, остальные распределяются
  по среднему полю и сортируются по высоте.
- Если пин в `wires` не найден — предупреждение в stderr, провод пропускается.
